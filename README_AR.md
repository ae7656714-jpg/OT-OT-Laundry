# OT Laundry — النسخة التأسيسية

هذه نسخة مشروع مستقلة جديدة، وليست تعديلًا على ملفات El Magd Accounting. تم إنشاء الهيكل الأولي لتطبيق Windows محليًا وربطه بخدمة مصادقة OT Laundry المنشورة على Supabase.

## الموجود حاليًا
- واجهة عربية RTL بهوية OT باللونين الأبيض والأحمر والرمادي.
- تشغيل محلي على `127.0.0.1` فقط.
- تسجيل دخول باسم المستخدم وكلمة المرور عبر Edge Function.
- في نسخة Windows المحلية تُحفظ رموز الجلسة داخل ذاكرة التطبيق. أما نسخة Vercel فتستخدم Cookie آمنًا يحتوي على رموز مشفرة وموقعة لتناسب التشغيل Serverless.
- تجديد جلسة Supabase باستخدام Refresh Token.
- شاشة الإعداد الأولي لإنشاء أول مدير.
- إدارة المستخدمين: إنشاء، عرض، تفعيل/إيقاف، تغيير اسم المستخدم وكلمة المرور.
- فرض صلاحية `users.manage` داخل Edge Function، وليس بمجرد إخفاء الأزرار.
- لا يوجد Service Role Key داخل التطبيق.

## الإعداد
1. ثبّت Python 3.11 أو أحدث.
2. شغّل `INSTALL.bat`.
3. افتح `.env` وأضف Supabase Publishable/anon Key فقط.
4. لا تضع `service_role` أو أي Secret Key في `.env`.
5. من Supabase Dashboard > Edge Functions > Secrets، أضف `OT_LAUNDRY_BOOTSTRAP_CODE` بقيمة قوية وفريدة. لا تشاركها مع أي شخص.
6. شغّل `START.bat`.
7. افتح `/first-setup` محليًا، واستخدم رمز التهيئة لإنشاء أول مدير. بعد ذلك استخدم شاشة الدخول العادية.

## حدود النسخة الحالية
هذه مرحلة تأسيس تسجيل الدخول وإدارة الحسابات فقط. الكاشير والفواتير والتشغيل والمدفوعات والتقارير والموارد البشرية لم تُنفذ بعد. لا تستخدمها لإدارة عمليات مغسلة حقيقية قبل اكتمال وحدات الأعمال واختبارها.

## ملاحظات أمنية
- Edge Function `quick-processor (الاسم المعروض: ot-laundry-auth)` تستخدم مفاتيح Supabase السرية من بيئة الخادم فقط.
- تطبيق Windows يستخدم Publishable/anon Key فقط.
- كلمات المرور لا تُخزن في جدول profiles؛ Supabase Auth يديرها.
- رمز التهيئة مطلوب لأول مدير فقط، ولا ينبغي وضعه داخل ملفات التوزيع.
- تعطيل المستخدم يتحقق منه مسار المصادقة، لكن يجب اختبار أثره على كل جلسات REST/RLS قبل الإصدار النهائي.

## تشغيل محلي واختبارات المرحلة
- التطبيق يستمع على `127.0.0.1` فقط ولا يفتح خادمًا على شبكة المكتب.
- تم فحص بناء ملفات Python نحويًا باستخدام `py_compile`.
- لم يتوفر Flask في بيئة البناء الحالية ولم يتوفر اتصال حزم خارجي، لذلك لم يتم تنفيذ اختبار تشغيل Flask end-to-end في هذه البيئة.
- لم يتم تنفيذ تسجيل دخول حقيقي أو إنشاء أول مدير؛ يتطلب ذلك إضافة المفتاح العام إلى `.env` وضبط سر التهيئة في Supabase.

## نافذة Windows
تمت إضافة `desktop.py` لاستخدام نافذة Windows مستقلة عبر pywebview بدل الاعتماد على فتح المتصفح يدويًا. هذه الطبقة تحتاج تثبيت الاعتمادات على Windows وتجربة WebView2 على جهاز التشغيل؛ لم يتم اختبار النافذة الأصلية على جهاز Windows داخل بيئة البناء الحالية.


## مرحلة الكاشير الأولية

أضيفت شاشة `/cashier` لقراءة أقسام الملابس والقطع والخدمات والأسعار المرتبطة بالفرع من Supabase باستخدام جلسة المستخدم وسياسات RLS. تتيح الشاشة تجربة الاختيار المرئي وبناء معاينة محلية للطلب وتعديل الكمية والخصم. **لا تحفظ الشاشة فاتورة ولا تسجل دفعة بعد**؛ زر الحفظ معطل عمداً إلى حين استكمال إجراء قاعدة بيانات ذري ينشئ الفاتورة وبنودها والتحصيل والحركة النقدية وسجل التدقيق داخل معاملة واحدة. يجب إضافة الأقسام والقطع والخدمات وربطها بالأسعار من قاعدة البيانات قبل ظهورها في الكاشير.


## المرحلة 1 — إعداد الكتالوج وإنشاء الفواتير
- شاشة إدارة أقسام الملابس وأنواع القطع والخدمات وربط القطع بالخدمات وتحديد السعر الافتراضي.
- إنشاء الخزائن بحساب افتتاحي صفر؛ لا يسمح بإدخال رصيد افتتاحي مباشرة دون حركة مالية.
- شاشة كاشير مرئية واختيار القطع والخدمات والكمية والخصم بالقيمة أو النسبة.
- حفظ الفاتورة عبر RPC بصلاحيات المستدعي (SECURITY INVOKER) داخل معاملة PostgreSQL واحدة، مع التحقق من الصلاحية والفرع عبر RLS وإعادة تسعير البنود من قاعدة البيانات، وتوليد رقم متسلسل للفرع ومفتاح منع التكرار.
- سجل الفواتير وعرض تفاصيل الفاتورة وطباعة إيصال استلام.
- الأسعار تحفظ كنسخة داخل بنود الفاتورة حتى لا تتغير الفاتورة عند تعديل أسعار الكتالوج لاحقًا.

### حدود المرحلة الحالية
- التحصيل والدفعات الجزئية وحركات الخزينة لم يتم تفعيلها بعد.
- حالات التشغيل المتقدمة (تحت التشغيل/جاهز/تم التسليم) لم يتم تفعيل واجهاتها بعد.
- الضرائب محفوظ لها حقول في قاعدة البيانات، لكن إعداد الضرائب واحتسابها من الشاشة لم يفعّلا بعد.
- إعداد الكتالوج يبدأ فارغًا في الفرع؛ يجب إضافة أقسام وقطع وخدمات وأسعار قبل إنشاء أول فاتورة.
- لا تعتبر هذه المرحلة إصدارًا إنتاجيًا نهائيًا قبل اختبارات المستخدم الفعلية، واختبارات الدفعات والصلاحيات والطباعة.

- تمت إضافة سياسات RLS محددة لسجل الحالة وسجل التدقيق ومفاتيح منع التكرار، ولا تعمل دالة إنشاء الفاتورة بصلاحيات مالك قاعدة البيانات.

## تحديث المرحلة الثانية — التحصيل على الفواتير

تمت إضافة واجهة تسجيل دفعة من صفحة تفاصيل الفاتورة. يتم التحقق من المتبقي وطريقة الدفع والخزينة في PostgreSQL داخل دالة `record_invoice_payment` بمعاملة واحدة، ثم إنشاء سجل الدفع وحركة الخزينة وسجل التدقيق. يدعم الطلب مفتاح idempotency لمنع تكرار تسجيل الدفعة عند إعادة إرسال الطلب.

### ترحيل قاعدة البيانات

تم تطبيق التغييرات على مشروع Supabase المتصل `OT-Laundry`، والملف `migrations/010_invoice_payments.sql` محفوظ للتوثيق وإعادة بناء البيئة. لا تعِد تشغيله يدويًا على نفس المشروع دون مراجعة، لأنه يحتوي على `CREATE OR REPLACE` و`CREATE POLICY`.

### ما لم يكتمل بعد

هذه ليست نسخة إنتاج نهائية. ما زالت تحتاج استكمال واختبار: دورة التشغيل وتحديث حالات القطع والفواتير، إيصال التسليم، المصروفات والتحويلات، الموارد البشرية والحضور والرواتب والسلف، التقارير، إعدادات الضرائب، النسخ الاحتياطي والاستعادة، واختبارات قبول كاملة على Windows والطابعات الحرارية.

## تحديث المرحلة الثالثة: التشغيل والتسليم
- تمت إضافة شاشة متابعة حالة كل قطعة: بانتظار البدء، تحت التشغيل، مكتملة.
- حالة الفاتورة تتغير تلقائيًا إلى `in_progress` عند بدء التشغيل، وإلى `ready` فقط عند اكتمال جميع القطع.
- لا يسمح بتسليم الفاتورة إلا إذا كانت `ready` وجميع القطع مكتملة.
- أضيف سجل لتغييرات حالة الفاتورة.
- تمت إضافة دالتي RPC في Supabase: `update_invoice_item_work_status` و`deliver_laundry_invoice`، مع فحص الصلاحيات ونطاق الفرع.
- يلزم أن يمتلك المستخدم صلاحية `invoices.status` لتحديث التشغيل أو تسجيل التسليم.

## تحديث المرحلة الرابعة — الكتالوج الثنائي اللغة وربط الكاشير
- الكاشير يقرأ الأقسام والقطع والخدمات من Supabase ويعرض الاسم العربي والإنجليزي.
- شاشة إعداد الأصناف تدعم إدخال الاسم العربي والإنجليزي للأقسام والقطع والخدمات الجديدة.
- أضيفت شاشة لتحديد سعر كل تركيبة (قطعة + خدمة) من داخل التطبيق، مع إبقاء الأسعار غير المحددة فارغة.
- الخدمة التي لم يُحدد سعرها تظهر في الكاشير كغير متاحة ولا يمكن إضافتها للطلب.
- أضيف تحقق داخل PostgreSQL يمنع إنشاء فاتورة إذا لم يكن لأي بند سعر محدد؛ لا يتم تحويل السعر المفقود إلى صفر.
- تمت إضافة كتالوج ابتدائي: 18 رجالي، 21 حريمي، 9 أطفال، و7 مفروشات/أخرى. الأسعار لم تُخمن.
- تم ربط 330 تركيبة قطعة/خدمة، وكل أسعارها NULL حتى يحددها صاحب المغسلة.
- ملفات التوثيق: `migrations/012_require_catalog_price.sql` و`migrations/013_bilingual_garment_catalog.sql`.

### استخدام شاشة الأسعار
1. افتح «الأصناف والخدمات».
2. في «تحديد أسعار القطع والخدمات» اختر القطعة والخدمة.
3. اكتب السعر بالجنيه واضغط «حفظ السعر».
4. ارجع إلى الكاشير أو حدّث صفحته؛ ستظهر الخدمة بالسعر الجديد.
- تحديث السعر يتم من خلال RPC باسم `set_garment_service_price` داخل معاملة واحدة؛ يحفظ السعر الحالي في `service_prices` ويحدّث السعر الافتراضي للتركيبة، مع فحص صلاحية `catalog.manage` ونطاق الفرع. راجع `migrations/014_set_garment_service_price.sql`.

- تمت إضافة زر طباعة إيصال التسليم من صفحة الفاتورة بعد اعتماد التسليم.
- تم ضبط إيصال الاستلام وإيصال التسليم للطباعة الحرارية بعرض 80mm (منطقة محتوى تقارب 72mm مع الهوامش). قد تختلف النتيجة حسب تعريف الطابعة وإعداد حجم الورق؛ اختبر من إعدادات الطابعة قبل الاستخدام الفعلي.

## تحديث المرحلة الثامنة — الموارد البشرية والحضور والرواتب والسلف

أضيفت وحدات الموارد البشرية إلى التطبيق وربطها بجداول HR الموجودة في قاعدة البيانات:
- `/hr`: دليل الموظفين، إضافة موظف بكود فريد، القسم، المسمى الوظيفي، تاريخ التعيين والراتب الأساسي، وإدارة الأقسام والورديات.
- `/hr/attendance`: تسجيل يومي لحالة الحضور (حاضر/متأخر/غائب/إجازة/عطلة)، الوردية، وقت الحضور والانصراف والملاحظات.
- `/hr/leaves`: تسجيل طلبات الإجازة ومراجعتها واعتمادها أو رفضها.
- `/hr/payroll`: إنشاء مسير رواتب للموظفين النشطين مع الراتب الأساسي والإضافات والخصومات وخصم السلف.
- `/hr/payroll/<id>`: مراجعة المسير واعتماده، ثم تسجيل صرف الراتب كاملًا أو على دفعات.
- صرف السلف وسدادها من شاشة الموارد البشرية؛ الصرف يسجل حركة خروج من الخزينة، والسداد النقدي يسجل حركة دخول.

### قواعد الرواتب والسلف
- ينشأ مسير الرواتب بحالة مسودة، ولا يمكن صرفه قبل الاعتماد.
- تُحفظ قيم الراتب الأساسي والإضافات والخصومات وخصم السلف وصافي الراتب كنسخة ثابتة داخل مفردات المسير.
- خصم السلفة من المسير يوزع على السلف المفتوحة الأقدم أولًا، وينشئ سجلات سداد مرتبطة بمفردة الراتب دون إضافة حركة نقدية وهمية للخزينة.
- صرف الراتب ينشئ سجلًا في `salary_payments` وحركة خروج نقدية في `cash_transactions` داخل نفس معاملة قاعدة البيانات.
- يمكن صرف جزء من صافي الراتب، ويظل المتبقي ظاهرًا حتى اكتمال الصرف.
- جميع عمليات السلف وصرف الرواتب والتحويلات المالية تتحقق من رصيد الخزينة قبل التنفيذ.
- تم إضافة صلاحيات `payroll.view` و`cash.view` لدور مسؤول الموارد البشرية؛ وتبقى صلاحيات الإدارة المالية الحساسة محدودة بالأدوار المصرح لها.
- دوال العمليات المالية الجديدة تستخدم `SECURITY INVOKER`، وتطبق نطاق الفرع وRLS والصلاحيات.

### حدود الاختبار
- تم فحص تركيب Python لجميع ملفات التطبيق.
- تم تحليل جميع قوالب Jinja بنجاح.
- تم اختبار سيناريو مالي داخل معاملة تجريبية تم التراجع عنها بالكامل: صرف سلفة، إنشاء مسير مع خصم سلفة، اعتماد المسير، صرف راتب على دفعتين، وسداد باقي السلفة نقديًا. اكتمل السيناريو، وتم التأكد من عدم بقاء أي بيانات تجريبية بعد `ROLLBACK`.
- لم يتم اختبار واجهات التطبيق من متصفح Windows بحساب المستخدم الفعلي؛ بيئة البناء الحالية لا تحتوي على Flask. يجب تثبيت المتطلبات وتشغيل `START.bat` ثم اختبار تسجيل موظف وحضور وإجازة ومسير راتب فعلي قبل الاعتماد التشغيلي.
- تحذيرات الأمان السابقة في Supabase لا تزال موجودة في دوال تسليم/تحديث حالة القطع `SECURITY DEFINER` وحماية كلمات المرور المسربة؛ وهي ليست ناتجة عن دوال HR الجديدة.

### حدود احتساب الرواتب في هذه النسخة
- يتم إنشاء المسير لكل الموظفين النشطين المسجلين في الفرع، ويُحفظ الراتب الأساسي الحالي كقيمة ثابتة داخل المسير.
- الإضافات والخصومات وخصم السلف تدخل يدويًا عند إعداد المسير؛ سجلات الحضور والإجازات متاحة للمراجعة لكنها لا تخصم تلقائيًا من الراتب في هذه المرحلة.
- لا يوجد حتى الآن احتساب تلقائي للعمل الإضافي أو التأخير أو الغياب أو النسب القانونية للضرائب والتأمينات الاجتماعية، ولا يوجد احتساب تلقائي للراتب النسبي عند التعيين أثناء الشهر. يجب مراجعة المسير وإجراء التعديلات قبل اعتماده.
- لا يتم تسجيل أي موظف تجريبي أو بيانات رواتب حقيقية تلقائيًا عند فتح الوحدة؛ يبدأ دليل الموظفين فارغًا حتى يضيف المستخدم بياناته.

## تحديث المرحلة التاسعة — الربط التلقائي بين الحضور والرواتب

أضيفت قواعد احتساب مستقلة لكل فرع، وتشمل:
- أيام العمل المحاسبية في الشهر.
- ساعات العمل اليومية.
- معامل أجر العمل الإضافي.
- معامل خصم التأخير.
- معامل خصم الغياب.

في شاشة الرواتب، يحدد المستخدم فترة المسير أولًا ويعرض النظام معاينة للحضور والغياب والتأخير والإضافي والمبالغ الناتجة. التأخير يحسب من وقت الحضور مقارنة ببداية الوردية بعد فترة السماح، والإضافي يحسب من وقت الانصراف بعد نهاية الوردية. تدعم الحسابات الورديات التي تعبر منتصف الليل.

يتم خصم الغياب من الأيام المسجلة صراحةً كغائب فقط، مع استثناء الإجازات المعتمدة. اليوم الذي لا يوجد له سجل حضور لا يتحول تلقائيًا إلى غياب حتى لا يتم خصم مبلغ دون تسجيل موثق.

عند إنشاء المسير، يعيد التطبيق قراءة ملخص الحضور من قاعدة البيانات، ثم يحفظ أيام الحضور والغياب ودقائق التأخير والإضافي ومبالغها داخل مفردات الراتب. يظل المسير مسودة حتى يراجعه المستخدم ويعتمده.

قواعد الاحتساب الافتراضية: 30 يومًا محاسبيًا، 8 ساعات عمل يوميًا، معامل إضافي 1.5، ومعامل خصم التأخير والغياب 1. يمكن تعديلها من شاشة «قواعد الرواتب». هذه قواعد حسابية قابلة للتخصيص وليست تحديدًا قانونيًا لمستحقات العامل.

ملف الترحيل: `migrations/021_attendance_payroll_automation.sql`.

## تحديث المرحلة الثالثة عشرة — حزمة Windows

أضيفت ملفات بناء Windows:
- `BUILD_WINDOWS.bat` ينشئ بيئة بناء ويثبت الاعتمادات ويصدر نسخة PyInstaller بنمط onedir.
- نسخة Portable في `release/OT-Laundry-Portable` مع `portable.flag` لتخزين إعداداتها داخل مجلد `data` بجوار البرنامج.
- `packaging/OT-Laundry.iss` لإنشاء Installer باستخدام Inno Setup 6، مع اختصارات سطح المكتب وقائمة Start.
- دليل المستخدم: `docs/USER_GUIDE_AR.md`.
- تقرير الفحص: `docs/RELEASE_QA_AR.md`.

لبناء ملفات EXE، شغّل `BUILD_WINDOWS.bat` على جهاز Windows 10/11 64-bit. إذا كان Inno Setup 6 مثبتًا فسيتم إنشاء ملف التثبيت تلقائيًا؛ وإلا يتم إنشاء Portable وتبقى خطوة تجميع Installer متاحة من ملف ISS. لم يتم تجميع أو تشغيل EXE داخل بيئة التطوير الحالية لأنها Linux.
